# Repository agent instructions

These instructions apply to work throughout **There Will Be Dungeons Transcripts**, including the skills under `.agents/skills/`. Read the relevant skill and project-specific editorial rules in addition to this file.

## Repository access and deliverable priority

**Use the first viable method in this exact order for reading, editing and delivering repository work:**

1. **Local file access** — Directly inspect and edit the current local checkout/filesystem when it is accessible and appropriate. Prefer targeted reads, local Git status/diffs and safe working-tree changes. Include local-only/ignored source archives where permitted; do not assume they are available remotely.
2. **MCP access** — If direct local access is unavailable or insufficient, use a connected workspace/project MCP service to search, read and make guarded edits to the correct local repository. Discover its supported actions and identify its actual workspace and revision. For this repository, a workspace may be exposed as `There Will Be Dungeons Transcripts/`.
3. **GitHub access** — If the first two routes cannot do the required work, use the GitHub repository connection/API, preferably a pinned branch or commit. Use GitHub for authoritative remote history/PR operations whenever those are the actual task; do not pretend a remote tree includes local-only or uncommitted files. The GitHub-specific connector falls under this third tier, even if it is technically an MCP integration.
4. **Git patches** — If an authorized live edit cannot be made using the preceding routes, provide a minimal, reviewable Git patch against an identified revision, with exact paths and application instructions. Do not describe an unapplied patch as a repository change.
5. **Zipped file bundles** — Use a ZIP containing replacement files only when the other four options are unsuitable, unavailable or explicitly requested. Include a manifest identifying paths, baseline and scope; avoid overwriting unrelated files and never package private audio/media or secrets without authorization.

**This is an ordered preference, not an instruction to try all five methods or duplicate every read.** Before selecting a route, check whether it can handle the operation and supplies the right repository revision. If a higher-priority route is stale, read-only, denied, lacks the necessary data or would endanger existing work, use the next capable route and note the reason. For tasks inherently involving GitHub PRs, remote refs or permissions, use the connected GitHub service for that action rather than manufacturing a local substitute.

**Re-evaluate the entire ordered access priority from the beginning at the start of every file-access batch, even if no tool has failed.** A file-access batch is a bounded group of related reads, edits or verification/checkpoint writes, including a newly started task, resumed work or the next file/group in a continuing task. Start again at **(1) direct local files**, then examine **(2) workspace MCP**, **(3) GitHub**, **(4) Git patches**, and **(5) ZIP bundles** in order until a capable, revision-correct route is found. **Never carry an earlier batch's “offline,” “denied,” or “unavailable” assessment forward as a standing assumption.** In particular, re-probe MCP on a later batch if local access is not viable, so a service that went down and then recovered is used automatically instead of remaining bypassed. Stop checking lower-priority methods once a suitable higher-priority route is confirmed; do not redundantly read or edit the same file through every method.

**Recheck access again during a batch** if the operation, target, permissions, repository revision or tool availability changes, or after a failed read, edit, upload, validation or required checkpoint. On failure first inspect whether the attempted operation partially succeeded, then **restart the priority check at (1)** rather than merely continuing from the previously chosen method; safely retry or select the first newly viable route, noting the reason. Do not silently skip a required edit or abandon a mandatory manifest/progress update because one route rejected it. Preserve the exact working-tree state, unrelated changes and already completed operations across method switches; never use a stale GitHub tree to overwrite uncommitted local files. If only a patch or ZIP can be produced, mark it **not applied**, provide precise application/reconciliation steps and record what remains pending; never call a required edit complete before verifying its persisted result. Method fallback does not authorize substantive changes, commits, pushes, merges or overwrites that still require owner approval.

**Guarded replacement validation:** Before calling a text-replacement tool, read the **current complete target text or a sufficient exact-context window** and verify that the literal replacement target occurs **exactly once**. Check Markdown emphasis, punctuation, whitespace, case and **actual LF/CRLF line endings** rather than reconstructing an assumed string from a numbered view. If the tool returns `edit_match_not_unique` or another match-validation error, do not classify that as a general server outage: reread the file, determine whether the match count is zero or multiple, select a genuinely unique exact anchor or more specific context, and retry after confirming no partial write. Only change access methods when the corrected operation is unsupported or still unavailable; never repeat a broad ambiguous replacement.

**Safety and provenance:** Check the checkout's branch, HEAD and working-tree status when possible. Never silently mix local, MCP and GitHub revisions or overwrite unrelated user changes. Use bounded source reads and guarded, unique-context edits; keep original recordings, source ASR, private maps and archived research intact. Treat successfully persisted edits, proposed patches and file bundles as distinct outcomes. Do not commit, push, merge or publish unless requested/authorized; never infer success or passing tests without checking.

## Preservation and reporting economy (owner direction D-052, 2026-10-29)

**Preserve meaningful baselines, not every intermediate edit.** Before a major rewrite, structural reorganization, extensive consolidation or destructive replacement of an existing document, capture the exact current working-copy bytes **once per affected document per coherent rewrite effort**, with SHA-256, original path, date, planned scope and archive/reference location. If that verified baseline already exists for the same effort and input state, **reuse it**; never generate another full-content copy merely because a batch, chapter, edit or agent turn changed. A separate new baseline is warranted when a distinct later major rewrite starts from a materially changed document. Preserve byte-locked accepted editions, original recordings, source ASR and other expressly protected records independently of this optimization. Git HEAD alone does not preserve uncommitted working-copy changes.

For ordinary bounded edits, minor copyedits, audits, incremental drafting, source checks, pointer updates and small follow-up repairs, **do not create whole-file pre-edit backups** by default. Use guarded edits, Git status/diffs, readback and relevant hashes to verify changes. Retain durable, concise **change and decision logs** (affected files, summary, rationale/evidence, approval, outcome, validation limits and next action) in the existing project decisions, manifest, progress and/or **one ongoing workstream journal**. Update these in place instead of archiving or reproducing their full contents before every update.

Use `reports/` for **independently useful findings** (e.g. substantive research, new evidence, comparisons or milestone reviews), not automatic one-report-per-task, per-chapter, per-status-check or per-retry paperwork. Prefer appending a short entry to a stable workstream log and linking to existing evidence. Recovery checkpoints may be updated after meaningful operations or interruptions **without creating a separate file each time**. Existing reports and `research/legacy/` artifacts are not retroactively disposable: inventory and propose deduplication, retain unique evidence and accepted baselines, and obtain approval before deletions or structural moves. This policy controls conflicting older per-operation snapshot/report wording in project plans and skills.

## Wastes adaptive batching (owner decision D-082, 2026-11-01)

For `$twbd-wastes-cleanup`, prefer **larger, coherent, dependency-safe cohorts**
instead of routinely performing four files or one WCL task per conversation.
Planning sizes: **10–15 short** files, **5–8 medium** files, **1–3 large/dense**
files, or several compatible low-risk editorial tasks, often **800–1,500
combined lines** for tractable inventories. These are flexible estimates,
not quotas or permission to omit individual checks. Preflight actual sizes,
source complexity, safety/tool limits, dependencies and authority; process
in bounded waves, checkpoint per-file evidence in the live census, and
complete each WCL checkbox independently. Prefer one compact task-register
update per coherent cohort; no redundant batch reports, extra backups,
full-suite verification or claims of tests not run. The [D-082 decision](project/DECISIONS.md)
and [cleanup skill](.agents/skills/twbd-wastes-cleanup/SKILL.md) supersede
older 2026-10-27 small-batch numeric guidance only for current Wastes work.
All other source, preservation, canonical-name, browser/audio and publication
safeguards remain unchanged.

**Minor-editorial autonomy (owner clarification, 2026-10-28; D-047):** Small, unambiguous spelling, typo, punctuation, grammar and reader-facing canonical-name/display corrections may be made without seeking separate approval. Check each referent in context and record the standing permission; preserve legacy paths, links, identifiers, direct quotations, evidence/uncertainty, original audio and source material. Verify bounded deltas against the current working tree. **Still request approval before any substantive, ambiguous or meaning-changing work**, including canon/identity determinations, historical reinterpretation, structural moves, renames, deletions and narrative rewrites. Do not turn a minor-copyedit exception into permission for wide or blind replacements.

**Project-wide reader-first presentation (owner direction D-048, 2026-10-28):** On **every new or revised reader-facing README, overview, index, narrative introduction and ordinary world-reference page**, lead with story, fictional world, lore and history. Put production/project-process notes, source/ASR methodology, audit status, links to reports, and illustration-generation records **last or in properly referenced Markdown footnotes**—not in the opening reader experience. Overview pages end with a clearly separated **Sources and project notes** section; in-universe subject pages end their story with **Current status/Lasting legacy**, then source footnotes. Do not automatically restore the illustration embeds the owner removed from **Fate 4** and **Dusthill**. This presentation rule applies to **Wastes, Delvers, Inverse, one-shots and bonus portals**, while original transcripts, source-first dossiers, technical instructions and specialist registers retain the functional evidence-first structure they need. **Full standard:** [reader-first presentation](project/READER_FIRST_PRESENTATION.md). This is not permission to rewrite lore, invent scenes or erase sources; roll out existing-page cleanup in bounded preserved batches under established substantive gates.
